# Development catalog startup

The reported errors had two causes: root dev launched only Next while its default catalog upstream was not running, and the standalone versioned API on port 4000 did not implement the storefront's `/api/products`, `/api/category` and `/api/banners` contracts. Its 404 envelope became null in the old adapter and then failed the array check. An HTTP 200 from a streamed storefront page did not establish that its catalog rendered successfully.

## Runtime commands and configuration

- `npm run dev`: build the maintained TypeScript compatibility adapter, start the full persistent API, verify the catalog, then start Next. Ctrl-C stops this launcher's children. Occupied ports are refused; other listeners are never killed or reused automatically.
- `npm run dev:api`: start the same full API alone, including both `/api` compatibility and `/api/v1` contracts.
- `npm run dev:api:foundation`: retain the old isolated versioned API, with database access disabled unless explicitly configured. Its apps/api env examples apply to this foundation command, not the full compatibility runtime.
- `npm run dev:web`: start Next alone. The caller owns API availability.

The full local service selects backend/.env.local first, then backend/.env. This fallback is authorized by the owner's explicit request to use the backend envs and the same production database in development. It preserves MONGODB_URI, including its database name, exactly; it does not copy credentials into the web workspace or tracked files. Dev selects development HTTP/cookie behavior and adds the exact local web origin in memory without changing the production configuration file. The development API and Next bind only to loopback; production listener behavior is preserved. The production root build/start contracts are unchanged. This command keeps the existing full service lifecycle, workers, routes and integrations; the API workspace foundation remains separately available rather than mounting an incomplete replacement.

Use backend/.env.development.example as a template for an ignored backend/.env.local. The example's URI is blank. Examples are not loaded and cannot activate a database. Alternatively, configure API_ORIGIN / LEGACY_API_ORIGIN in apps/web/.env.local to use an already-running full API; root dev performs a read-only compatibility check. A foundation API, unavailable database or non-array response now produces an actionable startup error before Next opens. Catalog runtime errors distinguish connectivity, HTTP failures, missing routes and malformed responses without including upstream payloads, URLs, queries or credentials. Only explicit product lookups treat 404 as a missing entity; a missing collection route remains an upstream error. Persistent category/banner caching and uncached price/stock reads are preserved.

Because the owner requested a shared production database, local admin/checkout writes and enabled workers would operate on that same data. No production connection, data mutation, credential retrieval, deployment or provider call was performed for this fix. There was no real backend runtime env file or database credential in this checkout; only templates existed before verification. The actual production connection cannot be verified until the owner supplies it through an ignored runtime file.

## Verification

Lint, complete typecheck and isolated Turbopack production build passed. Unit regressions cover command port/origin validation, exact shared-URI preservation with independent development HTTP settings, wrong-API startup rejection, malformed/error response redaction and missing product versus missing route behavior. The full unit suite passes 113 cases and all 110 API/security/provider regressions pass.

A real, newly created loopback MongoDB replica set and temporary ignored backend/.env.local exercised the normal full-service launch path. The source config used production environment labels; dev preserved the same synthetic database and selected local HTTP behavior without editing the file. The temporary configuration and database were removed after verification. Next ran on 4760, API on 4770, with isolated dev output so the existing dev server's cache was preserved.

Home, products, categories and offers rendered their synthetic catalog, including direct navigation/reload. Browser console/network and Next `/_next/mcp` compilation/error diagnostics were checked. The 360, 390, 768 and 1280 px viewports had no horizontal overflow. React inspection confirmed server catalog rendering with the existing client cart islands. The API-only launch also returned HTTP 200 for both compatibility category/product arrays and versioned status, bound to 127.0.0.1, and did not launch Next. Shutdown removed the owned API listener and temporary configuration. The synthetic placeholder image caused an existing LCP loading suggestion; this task does not change image loading policy. These checks establish local startup/contract behavior, not production database availability or hosted acceptance.
