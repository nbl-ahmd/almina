## Scope and account setup

staff mailboxes and incoming replies. The root Microsoft MX is unchanged. No staff
mailbox or paid subscription was created. The setup follows https://resend.com/setup.md.
Official Resend, email-best-practices and CLI skills were installed outside the repository;
the OAuth MCP connection was authorized by the owner.

Both sending domains are verified in the pharmacy.spmb Resend team, Ireland region:

- `news.alminapharmacy.com`, ID `9c1d7aac-b2a0-4d50-8def-8b0cdbf8a05b`.

Approved DNS additions: two DKIM TXT records; `rsend.notify`/`send.notify` CNAMEs;
`rsend.news` CNAME; `send.news` MX/TXT for bounce processing; initial root DMARC
`v=DMARC1; p=none;`. The existing Microsoft root MX and SPF were preserved.
Open/click tracking is disabled on both domains. DMARC enforcement should only be
strengthened after all legitimate senders, including Microsoft 365, are checked.

Two separate sending-only API keys were created, each restricted to its domain:
**Al Mina website transactional** and **Al Mina requested reminders**. No full-access
setup credential is given to the production application. Private credentials are

## Code and boundaries

- `EMAIL_PROVIDER=resend` explicitly selects the new provider. Without it, existing
  Microsoft SMTP paths remain compatible. Google sign-in and guest checkout remain.
- Email-code sign-in retains HMAC, expiry, attempts, account uniqueness and session
  ownership. Resend readiness replaces the old mandatory SMTP-password check.
- Order confirmation uses the committed order's recipient, order number and immutable
  total. Existing outbox leases/retries remain; each order has one stable Resend
  idempotency key. Provider deduplication lasts 24 hours, not forever. Order creation
  and inventory commits never depend on email success. Both production adapters use
  the same maintained provider.
- Creating an approved business invitation attempts email delivery. The admin action
  explicitly says it emails the invitation. Failure/unconfirmed acceptance still
  returns the valid private link and a clear manual-sharing fallback. Invitations
  remain email-bound, seven-day, single-use, and require verified sign-in/approval.
- Existing requested cart/restock/price-drop/replenishment logic remains owner-scoped,
  one-shot, cancellation-aware and restricted to reviewed general-sale products.
  It does not silently enrol customers or infer consent from abandoned guest carts.
- Atomic shared MongoDB counters cap application attempts at 100/day and 3,000/month;
  optional reminders additionally stop at 20/day and 500/month. Limits are conservative:
  failed attempts/retries count, and provider dashboard sends/inbound traffic are not
  included. These are Free-plan limits and need adjustment when upgrading. Budget-
  blocked reminders defer; uncertain sends retain the existing no-blind-resend policy.
- Account/order API requests use bounded deadlines and stable idempotency keys;
  transient network/429/5xx errors receive at most one short backoff retry, respecting
  Retry-After (longer delays are left for the caller/outbox). Other 4xx are not retried
  inside the adapter. Provider diagnostics are not logged or exposed.
- `/api/v1/email/webhook` verifies Resend/Svix signatures, timestamp and raw body.
  Replay-safe event records store only operational metadata and hashed recipients.
  Hard bounces suppress all application sends; complaints suppress reminders. Resend's
  own suppression rules also apply. Later delivered events cannot undo suppression.
- `/api/v1/email/unsubscribe/:token` supports RFC 8058 one-click POST using the
  unguessable reminder token; ordinary GET cannot cancel anything. The existing
  storefront cancellation link remains available. This endpoint's form content type
  is allowed only for its exact POST path; ordinary API JSON protections remain.

## Activation and rollout

Required server-only Render values:

```
EMAIL_PROVIDER=resend
RESEND_API_KEY=<transactional sending-only key>
RESEND_MARKETING_API_KEY=<reminder sending-only key>
RESEND_WEBHOOK_SECRET=<webhook signing secret>
EMAIL_TRANSACTIONAL_DOMAIN=notify.alminapharmacy.com
EMAIL_MARKETING_DOMAIN=news.alminapharmacy.com
EMAIL_REPLY_TO=info@alminapharmacy.com
EMAIL_PUBLIC_API_ORIGIN=https://almina-of4b.onrender.com
GROWTH_WEB_ORIGIN=https://alminapharmacy.com
GROWTH_EMAIL_ENABLED=true
```

Keep the existing `CUSTOMER_AUTH_SECRET`; do not rotate it as part of this setup.
The owner must privately enter/submit new credentials in Render because browser
credential changes require a human handoff. These values are not frontend/Vercel
public environment variables. Existing environment values must not be replaced.

The delivery webhook is registered at
`https://almina-of4b.onrender.com/api/v1/email/webhook` for sent, delivered, delayed,
bounced, complained, failed and suppressed events. It becomes reachable when this
code is deployed. Registration alone does not prove the live endpoint is healthy.

When explicitly configured for Resend, startup additively prepares the existing
planned auth-code/auth-limit TTL indexes and requested-reminder indexes plus 30-day
TTL indexes for new `email_events` and `email_delivery` collections. Preparation is
idempotent; index conflicts stop startup instead of dropping/replacing anything.
`email_usage` and `email_suppressions` use their built-in unique `_id` indexes.
Monthly counters and suppression hashes are retained. No customer/order/catalogue
records are rewritten. Rollback: disable `GROWTH_EMAIL_ENABLED` for reminders; revert
`EMAIL_PROVIDER` only if the old SMTP credentials actually work. Keep additive data
and indexes. Do not drop collections or delete suppression records during rollback.

After release and private configuration, enable desired reminder types in
Admin → Website & growth → Requested reminders. The existing policy remains inactive
until explicitly enabled. No contact list was imported, newsletter campaign sent,
or loyalty/offer rule invented by this setup.
