# Modernization foundation

Implemented 2026-10-02 on branch `modernization/foundation`, following the completed production audit. This is an additive, independently verified foundation. **It is not a production cutover or remediation of the audit's legacy security/commerce findings.** No database/provider connection, schema/index change, customer-data access, integration replacement or deployment was performed.

## Architecture and ownership

| Location | Responsibility |
| --- | --- |
| `apps/web` | Next.js App Router with Turbopack, TypeScript, Metadata APIs and loading/error/not-found boundaries. Server Components by default; only error recovery uses Client Components. Preview `/` and dynamic `/foundation/status` only. |
| `apps/api` | Separate persistent Express 5/Node process, typed errors, bounded JSON parsing, public health/status endpoints and graceful shutdown. No legacy router/startup imports or commerce writers. |
| `packages/contracts` | Zod runtime validation, versioned success/error envelopes, typed API client, bounded explicit pagination, separate PD business-ID/ObjectId validators. |
| `packages/config` | Strict TypeScript defaults, ESLint configuration, validated server settings and structured operational logger. |
| `packages/ui` | One small server-compatible page-content primitive; no new design system or storefront redesign. |
| `scripts/migrations`, `scripts/backfill`, `scripts/media` | Guarded reserved directories; no executable data-migration scripts yet. |
| `scripts/tooling` | Version-matched documentation locator, route-type generation, compiled API build and isolated production smoke verification. |

`frontend/` and `backend/`, their manifests/lockfiles, data schemas, routes, media and integrations remain intact and outside npm workspaces. New processes never load `backend/.env`. The existing favicon is copied byte-for-byte into the new web app to avoid browser asset 404s; no existing media is moved/deleted. Fonts remain system fonts and there are no content images in this placeholder; `next/font`/`next/image` will apply when verified routes acquire those assets.

No production URL ownership changes. Preview pages are always `noindex, nofollow` via metadata and response headers, including when running in production mode. Configure a separate preview/staging host. Remove this restriction only as part of a reviewed route cutover after security/integrity gates pass.

## Version selection and documentation

Registry checks identified Next **16.3.8** as the highest stable 16.x release. The [September 30 security release](https://nextjs.org/blog/september-2026-security-release) recommends this patch. Its package engines require Node >=20.9 and its React peer range accepts React 19. Node **24.21.0 LTS**, with bundled npm **11.19.0**, was selected from the official Node release index and installed for verification. Node 26 is not selected because this task requires current LTS. [Node 24.21.0 release](https://nodejs.org/en/blog/release/v24.21.0).

Run `npm run docs:next` to print the installed Next version and resolve its documentation directory from `apps/web`, independent of npm hoisting. Root and web `AGENTS.md` direct future agents there. The managed Next agent block generated by `next dev` is preserved. Implementation consulted these **installed 16.3.8 bundled docs** under `next/dist/docs/01-app/`:

- `01-getting-started`: installation, layouts/pages, error handling, metadata.
- `02-guides`: environment variables, AI agents/MCP.
- `03-api-reference`: error/loading/not-found conventions, `connection()`, TypeScript, ESLint, Turbopack and `transpilePackages`.

Version-specific decisions: explicit Turbopack commands and workspace root; direct ESLint CLI (no `next lint` or build-time lint assumption); `retry()` error recovery; `connection()` before runtime API/environment reads; automatic workspace transpilation without an unnecessary `transpilePackages` list. No CRA `REACT_APP_*`, React Router, Helmet, `%PUBLIC_URL%`, SPA fallback or client-loaded environment assumptions are introduced.

## Local commands

```sh
nvm install
nvm use
npm ci
npm run dev:api                 # loopback :4000; database disabled
npm run dev                     # another terminal, Turbopack on :3000
npm run typecheck
npm run lint
npm test
APP_ENV=development npm run build:foundation
npm run smoke:foundation
```

No env file is needed for isolated local development. Optional setup: copy each app's `.env.development.example` to that app's `.env.local`, leaving `DATABASE_MODE=disabled`. Never copy legacy `.env` files. The API dev command uses Node's explicit `--env-file-if-exists=.env.local` from its own app directory; API production startup loads only injected process settings. Next follows its documented app-local env-file precedence; do not package `.env.local` in deployment artifacts.

Stop development watchers before `npm ci` or dependency reinstallation. Replacing `node_modules` under live Next/tsx watchers caused transient resolution errors during verification; restarting both processes after install restored clean runtime checks. Preserve `.next` while a dev server is running.

Production artifact entry points are `npm run start:web` and `npm run start:api`. Alternate web smoke port: `APP_ENV=development npm run start:web -- --port 3100`. API: `APP_ENV=development NODE_ENV=production PORT=4100 npm run start:api`. The API bundle externalizes its declared Express/MongoDB/Zod dependencies; deploy it with its npm workspace dependencies, not as a standalone executable. Web production startup uses `next start`; choose a deliberate reverse proxy/host command for deployment (local scripts bind to loopback).

The root **`build` and `start` are still the original legacy deployment commands** because the audit could not verify the active host's build contract. Do not use them to verify the foundation: root `build` installs legacy backend packages and root `start` launches the unsafe audited backend. New CI uses `build:foundation` explicitly. Changing production host commands or switching root defaults is a later coordinated rollout. Root engine enforcement now requires Node 24/npm 11; an existing deployment that installs from the root on older Node must be reviewed before taking this branch. Legacy runtime compatibility on Node 24 is unverified.

## Environment separation

Each app has development/staging/production `.example` files containing only non-secret settings and reserved `.invalid` deployment domains. Examples are templates, not automatically loaded deploy configs. For staging/production, supply independently scoped platform settings/secrets, use `NODE_ENV=production` and select `APP_ENV=staging` or `production`. Do not invent `NODE_ENV=staging`: Next's modes differ from deployment environments.

| Setting | Policy |
| --- | --- |
| `APP_ENV` | Defaults to development only outside production Node mode. Production build/start requires an explicit environment. |
| `WEB_ORIGIN`, web-only `API_ORIGIN` | Loopback defaults only for development. Other environments require explicit HTTPS origins; credentials, paths, query strings and fragments rejected. |
| `LOG_LEVEL` | `info`, `warn`, `error`; no body/PII debug mode. |
| `API_HOST`, `PORT` | Typed host allowlist and bounded numeric port. Dev defaults to loopback; deployment API host defaults to `0.0.0.0` behind host/network controls. |
| `DATABASE_MODE` | Disabled by default in every example. Supplying database settings while disabled fails closed. |
| `DATABASE_ENV` | Required when enabled and must match `APP_ENV`. This catches configuration mismatch; it cannot prove a credential belongs to the intended cluster. |
| `MONGODB_URI`, `MONGODB_DATABASE` | Required only for explicit database activation; separate named DB, secret-manager URI and least-privilege credentials. Non-dev requires Atlas-style `mongodb+srv`. TLS verification is enforced for SRV connections. |
| `NEXT_PUBLIC_*` | No public settings are defined; unexpected public variables rejected. No config `env` injection, secret serialization or client credential handling. |

Staging must use a separate sanitized database and scoped credentials; production database-name/host verification and backups remain required before activation. No copying of production data/settings is authorized by these examples. Invalid configuration reports field names only. Secret files/build outputs/logs are ignored; `.gitignore` does not revoke or untrack the credential material identified in the audit. Its rotation/revocation remains outstanding.

`next typegen` runs in production mode. Its wrapper explicitly selects development for static tooling when the caller supplies no `APP_ENV`; this makes plain `npm run typecheck` work without weakening build/start validation. Staging/production selections can still be passed explicitly. All build/test/smoke checks run without DB/provider credentials.

## API, logging and database conventions

- Only `GET`/`HEAD` `/health/live`, `/health/ready`, `/api/v1/status` exist. Query keys are rejected on these endpoints. Unsupported methods return 405/Allow; unknown routes return 404. No wildcard CORS or proxy trust is enabled.
- Responses use `{data, requestId}` or `{error: {code, message}, requestId}`. Request IDs are server-generated, returned in `X-Request-ID`, and supplied client IDs are ignored. Responses are `no-store`. Readiness failures return 503/Retry-After; liveness never probes the database.
- Status declares `disabled`, `ready` or `not_checked`. A disabled DB means the **foundation process** is usable, not that shopping/checkout is ready. There are no commerce endpoints. Public health returns no DB name, URI, environment details or customer data.
- JSON parsing is bounded at 16 KB. Domain endpoints must add specific request/response schemas and server auth/RBAC before mounting; pagination contracts never accept raw query filters. No placeholder authorization middleware claims to secure the existing API.
- Logs allowlist operational event, service/environment, generated request ID, method, fixed route pattern, status and duration. Error text/stacks, URLs/query strings, headers, bodies and arbitrary context fields are omitted. Future action audit logs require deliberate non-PII identifiers and retention policy.
- The API owns a lazy shared MongoClient pool, bounded connection/query timeouts, failure cleanup/retry, readiness ping and graceful close. No connection during module import/build/test. No Mongoose schema duplication, index automation, collection relocation or business-data writes. `getDb()` is an internal boundary for future reviewed repositories, never an HTTP raw-query interface.
- The shared fetch client validates the response envelope at runtime, bounds requests at five seconds, rejects redirects/unsafe origins, supports caller abort, uses `no-store` and omits browser credentials. The web wrapper is guarded by `server-only`; ESLint restricts server config imports to guarded web modules/config. Session/CSRF/auth adapters are intentionally pending the legacy security phase.

Removed root-only `@novu/node`, `in`, `terminal`, `your`: audit and repository import checks found no consumers. Their transitive trees disappear from the root lockfile. The root's nonexistent `index.js` main entry is removed. No legacy frontend/backend dependencies were removed. Root `pm2` is pinned to its previously locked **5.3.0** to preserve the existing `pm2-runtime` command; it is not used by either new application.

Conflicts requiring follow-up:

1. **PM2 legacy tree**: final root advisory report has **23 affected package entries** (4 low, 4 moderate, 13 high, 2 critical), all in the retained PM2 dependency tree. Do not call the root install security-clean or deploy this foundation as remediation. Removing/replacing/upgrading PM2 requires checking production process management and testing the major upgrade independently. No force audit fix was run.
2. **ESLint support**: npm marks 9.39.5 deprecated. Latest ESLint 10 does not satisfy the current `eslint-plugin-react`/`eslint-plugin-import` peer ranges used by Next's config. This foundation pins a working compatible stack; review a supported lint stack once those peers update, without overriding incompatible majors. [ESLint support policy](https://eslint.org/version-support/).
3. **Zod dev/runtime duplication**: DevTools internally uses Zod 3; production code uses Zod 4. An initial compiled API startup resolved root Zod 3 and failed even though source tests/build passed. Explicit API runtime dependency plus compiled startup smoke fixes and guards this boundary. The tooling version is not a second application validation system.
4. **Shared source resolution**: `.js` relative imports in shared TypeScript were not resolved by this Turbopack build. Contracts now use bundler-compatible extensionless source imports; the API bundles internal packages so Node does not need to execute workspace TypeScript exports in production.
5. **Legacy deploy defaults/engines**: root build/start stay legacy; Node/npm enforcement changes root installation prerequisites. Confirm hosting before promotion. No deployment/session/reverse-proxy compatibility is claimed.

Global `agent-browser` 0.38.2 was installed as verification tooling alongside Node 24.21.0; it is not a project/runtime dependency. npm 11 reported unapproved install hooks for esbuild, fsevents and unrs-resolver. No global allow-scripts setting was changed; optional platform binaries supported the completed clean install/build/lint locally. Linux CI remains to be run by the repository's CI service.

No audit P0/P1 closure is claimed. Rollback is to keep the existing deployment/route ownership; there are no database/schema writes to undo. Security and commerce fixes remain prerequisites to moving production storefront/checkout traffic.

## Security release update — 22 October 2026

The initial 16.3.8 selection above is historical. During email/wholesale release
verification, GitHub's audit feed flagged GHSA-2464-fhr4-w9xw (image optimization)
and GHSA-p3m5-59mp-jv5r (Server Actions). Both affect 16.x through 16.4.0; patched
16.4.1 is the minimum. The npm registry's current stable 16.x/latest is **16.4.2**,
so web Next and matching ESLint packages are pinned to 16.4.2 with the lockfile.
Node 24.21.0 meets its >=20.9 engine; existing React/React DOM 19.3.0 satisfy the
published React ^19 peer range. No unrelated runtime dependency upgrade is intended.

Reviewed upstream 16.4.0, 16.4.1 and 16.4.2 release notes and the bundled Next 16
upgrade guidance. Existing App Router, async request APIs, proxy, Turbopack and
server/client boundaries remain. Resolve/read the newly installed version-matched
bundled docs using `npm run docs:next`. SVG image optimization remains disabled.
Release verification must include the full security gate, API tests, production
build/browser journeys and live Turbopack diagnostics before merge/deployment.

References: [16.4.2 release](https://github.com/vercel/next.js/releases/tag/v16.4.2),
[image optimization advisory](https://github.com/advisories/GHSA-2464-fhr4-w9xw),
[Server Actions advisory](https://github.com/advisories/GHSA-p3m5-59mp-jv5r).
