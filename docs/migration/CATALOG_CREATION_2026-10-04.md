# Retained catalog creation ownership

`POST /api/products` and the non-recovery `POST /api/batch` now delegate persistence to `apps/api/src/modules/catalog/creation.ts`. URLs, authorization, populated create response, explicit category/barcode input and the batch's `PD5000` allocation floor remain compatible. The old batch importer remains blocked before disk upload in recovery mode; the maintained domain also checks the bootstrap marker inside its transaction.

Single and batch creation previously independently downloaded every product and derived IDs, permitting duplicate IDs under concurrent calls. The maintained allocator uses a bounded server-side numeric `PD` prefix aggregation and a shared additive `catalog_counters` high-water record. It preserves retained/recovered IDs and serializes on the store document used by recovery imports, so a concurrent recovery import cannot insert the same next ID. Product creation, category creation, counter changes and append-only initial-stock ledger entries commit together. Batch input is validated in full before writes, at most 500 rows in a 2 MiB upload. Ambiguous/archived categories and unsafe money/stock fail closed. Barcodes remain strings and no filename-derived identity is used. The request's temporary CSV is cleaned up; media is retained.

No existing identifiers, prices, stock, order history or fields are backfilled or rewritten. Initial-stock ledger entries start with new creation only and record authenticated actor, reason, before/after and delta. Recovery remains a separate reviewed workflow inserting disabled drafts with zero stock and keeping the store closed.

## Verification and limitations

Real disposable MongoDB tests race four single creations with three two-row batches: ten distinct sequential IDs, one new category and ten initial-stock receipts. They verify whole-transaction rollback after category creation, no counter/stock/ledger partial changes, retained identifiers/stock, leading-zero barcodes, invalid money/sales/stock/category rejection and recovery blocking. The retained HTTP create/read/update tests exercise the older Mongoose driver's transaction behavior as well as the current native driver. Do not rely on the value returned by `withTransaction` across driver versions; results are captured explicitly.

All 29 mandatory real-database/load tests, 59 unit, 99 API/security/upload and 7 release-gate regressions passed; lint/typecheck, foundation build and all 26 Chromium regressions passed. All three lockfile audits report zero high/critical advisories. The first build invocation omitted required development origins and correctly failed configuration validation; the explicitly configured, database-disabled build passed.

Drive upload and retained image read adapters still exist. Upload acceptance followed by database failure may leave an unreferenced retained asset; never delete it automatically. Initial creation and the historical batch URL have no request-idempotency contract: after an uncertain response, reconcile the admin listing before resubmitting. Stock adjustment, recovery commit, signed replacement and checkout retain their explicit retry receipts. Category/banner/staff and WhatsApp/push ownership and live-provider parity remain separate work.

Apply the additive product business-ID index plan only after review; the allocator is bounded by a 3-second aggregation deadline and fails rather than guessing on timeout. Production duplicate inventory is still required before any unique index. Old binaries do not honor this allocator: run one catalog-writing application version at a time during staging/cutover and pause writes for rollback. Keep the counter/ledger fields when rolling back, and do not restore old database snapshots over later orders or stock.
