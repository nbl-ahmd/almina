# Maintained SMTP provider boundary

`notifications/email.ts` now owns persisted-order confirmation content, bounded administrative email validation, fixed SMTP policy, acceptance validation, overall deadlines, cancellation and redacted failures. The retained `order-email.cjs` adapter supplies hosting credentials and Nodemailer through `smtp.cjs`; `/api/orders/email` keeps administrator authorization and its successful 204 response. Missing configuration/provider failures return a generic 503 instead of leaking SMTP diagnostics. Invalid input returns 400 before provider work.

Confirmation recipients and deterministic `<almina-order-OD…@alminapharmacy.com>` message IDs still come from persisted orders. Caller HTML/destinations never affect confirmations. Administrative emails retain the existing subject/from/HTML contract, with one bare email recipient, strict keys, no attachments and a 64 KiB UTF-8 HTML limit. This remains a privileged administrative tool, not public email sending. `SMTP_USER` must be a bare email address and credentials must be injected by hosting; nothing reads backend `.env` during verification.

The provider remains `smtp.office365.com:587`, with mandatory STARTTLS, verified certificates/TLS 1.2 minimum, bounded DNS/connect/greeting/socket timeouts, and a 15-second overall deadline. File/URL access and protocol logging are disabled. Success requires explicit acceptance of the one intended recipient with no rejected recipients. See [Nodemailer SMTP options](https://nodemailer.com/smtp). No provider, account, authentication mode or delivery destination was changed.

Inspection of installed Nodemailer 10.0.14 found that non-pooled `transport.close()` alone does not close an active SMTP send. The small retained provider adapter owns the TCP socket through Nodemailer's supported `getSocket` transport option. Closing destroys that socket, including a STARTTLS connection, before transport cleanup. A real Nodemailer test against a disposable loopback server verifies stalled-greeting timeout and socket destruction. Domain tests cover cancellation, late rejection, malformed/rejected acknowledgment, outage, credential failure, cleanup failure and exactly one send attempt. No actual provider message was sent.

The adapter never retries. Existing durable order jobs retain their atomic order/outbox contract, leases, drain, bounded backoff and at-least-once retries. SMTP acceptance followed by lost acknowledgment or failed receipt persistence can still duplicate mail; a deterministic Message-ID is not a delivery deduplication guarantee. Administrative sends have no durable receipt: after uncertain responses, operators must reconcile provider records before manually resending. Do not claim inbox delivery from a successful SMTP response.

Local evidence: 68 unit regressions including four provider tests, 101 API/security, 36 mandatory real database/load and 7 release-gate tests passed; lint/typecheck, isolated Next/API production builds and all three lockfile audits passed. The first build without explicit development origins failed closed and was rerun with the documented isolated environment. Protected CI must repeat the full compiled browser suite before acceptance.

Rollback keeps the unchanged outbox schema and message ID; preserve restricted transport/deadline behavior when reverting application routing. No legacy fields were contracted. Hosted TLS/authentication, sender authorization, synthetic inbox delivery, outage/drain and duplicate reconciliation remain mandatory acceptance gates. WhatsApp outbound, push and Drive ownership remain separate work.
