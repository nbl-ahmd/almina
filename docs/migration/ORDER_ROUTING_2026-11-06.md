# Pharmacy order receiving and deterministic branch routing — 2026-11-06

## Previous behaviour

Staff order access and push recipients depended on exact `customer.city` text matching `users.cities`. A typed spelling difference, OSM neighbourhood label or empty staff assignment could hide an order from that staff account. Administrators retained access. Public branch-directory areas were presentation/serviceability data, not order ownership.

## New configurable setup

Administrators configure operational branches in **Users → Order routing**. Stable UUID branch IDs are independent of the public directory and branch names can change without changing access. Select RAK areas from a searchable English/Arabic reference; one canonical area can belong to only one branch. A required fallback branch receives **all** unselected areas, unknown names and other emirates. Several accounts may belong to one branch without creating duplicate orders.

Save a draft first, assign existing and new staff to branches, then activate. Activation requires every active staff account to have a valid branch and every routing branch to have an active staff member. Moving/deactivating the last staff member of an active branch is blocked. Administrators always see all orders, including before activation and when an address cannot be resolved. Draft mode deliberately preserves old city permissions until the operator switches. Disabling routing explicitly restores those legacy permissions.

Branch ownership uses the current published configuration for both historical and new orders; changes immediately move the relevant queues. List, detail, confirmation, packing, dispatch, cancellation and push recipient selection share the same server-side branch rule. Staff with a missing/deleted branch fail closed. All new privileged endpoints enforce existing identity, Origin/CSRF and retained allowlist rules. Configuration and staff edits serialize through the existing staff-administration control transaction, with revision/expected-branch conflict checks and audits. Client-supplied roles, branch ownership and totals are never trusted.

## Area reference and matching

Reference: OSM/Geofabrik [GCC snapshot 2026-11-04](https://download.geofabrik.de/asia/gcc-states-261104.osm.pbf), inside OSM [RAK emirate boundary relation 3766485](https://www.openstreetmap.org/relation/3766485). The saved list contains 182 canonical places from 200 named settlement/neighbourhood nodes and ways. It includes inland RAK areas and avoids the Oman/UAE bounding-box overlap. Place ways use a representative centre for this offline catalogue extraction, not delivery polygon matching.

Attribution: © [OpenStreetMap contributors](https://www.openstreetmap.org/copyright), [ODbL 1.0](https://opendatacommons.org/licenses/odbl/1-0/). The derivative reference is shared in `packages/contracts/src/rak-delivery-areas.ts`; source-object provenance is in `docs/migration/data/RAK_AREAS_2026-11-04.json`. Nearby duplicate place representations sharing an exact name/Arabic alias are grouped; Al Jazeera/Al Jazirah transliterations and Al Nakheel/Nakhil are explicit curated equivalents. No dependency, map API request or geocoder autocomplete is added to storefront runtime.

The public Overpass instances were unavailable during setup. A single cached regional extract was processed locally instead. Extraction uses Python osmium/shapely outside production; no provider secrets, customer addresses or customer coordinates were sent. The source snapshot is a reference and can omit districts; it is **not** proof of delivery boundaries or exhaustive coverage. Refreshes need a reviewed migration preserving existing canonical IDs, not an automatic replacement.

New checkout stores additive `routing: { version: 1, areaId, revision: 0 }` metadata. Original customer city/address remain immutable. Known aliases, case, spaces and punctuation use one deterministic resolver; emirate must also match RAK. Other emirates and unknown/ambiguous names resolve to null and reach fallback, with address review required. No fuzzy spelling guess grants access to a branch. GPS reverse-geocoded labels and typed addresses go through this same resolver. No new delivery eligibility/fees or geofencing rule is introduced.

Historical orders with no versioned metadata use an equivalent MongoDB expression, preserving coverage before backfill. Indexed versioned routing is the normal path. `scripts/migrations/order-routing.ts` defaults to an offline plan; explicit `--apply` adds only missing metadata in bounded batches, is repeatable, and never overwrites manual review or changes prices, stock, customer text or identifiers. Apply the additive API index plan and backfill before activating on a large production order history; the legacy expression can be expensive until then. Migration output contains counts only. No production backfill has been run by this task.

## Receiving and alerts

The admin header shows connection state, a linked count awaiting confirmation, an explicit optional **Enable sound** action, and a persistent attention link for newly observed pending orders. Sound is browser-user initiated, short Web Audio (no downloaded asset), session-only and occurs only while the page is open and audio is allowed. It is not an alarm/delivery guarantee. SSE reconnects retain the previous efficiency fixes; the snapshot is now a bounded operational digest, not full customer/order payloads. The existing SSE connection carries only a waiting count and up to ten authorized opaque order IDs; it does not create a second continuous poll or expose names, emails or address details. Polling remains a connection fallback. Aggregate counts and the paginated inbox remain the source of truth; the newest-ten attention sample is not a replacement for all waiting orders.

Orders shows waiting and address-review counts and oldest waiting time in UAE time. Only cash or verified live-paid card orders contribute to fulfilment-ready waiting signals; awaiting/test card payments stay visible in the order list but are not announced as ready. Existing server payment guards remain authoritative. Pharmacy staff have direct **Confirm order** and **Mark as packed** commands, using the existing transactional, idempotent lifecycle. No automatic acceptance, inventory deduction or billing change occurs from an alert.

Background push uses the same current branch assignment, also alerts administrators, preserves durable receipts and retry/quarantine handling, sends no customer payload and requests high urgency. It still requires deployed VAPID configuration, browser permission, an active subscription and provider/network availability. An expired subscription is removed; delivery remains best-effort. Alert settings do not activate or configure third-party credentials.

Unknown addresses remain visible in the fallback and administrator queues. An administrator can verify an area with the customer and record a reason; a revision-checked transaction updates only routing and writes an audit. This moves queue visibility without rewriting the original address, totals or order history. An open receiving screen observes moved pending orders. The same correction transaction also creates an idempotently keyed staff-only push job for the current receiving branch and administrators; its email state is `not_required`, so the customer confirmation worker cannot send another email. No duplicate order is created.

## Release and rollback

This branch does not configure real branches, assign production staff, change production delivery rules or activate routing on behalf of the owner. All business configuration is left for administrators as requested. Deploy both the maintained API and web changes together (API first while feature remains inactive), apply additive indexes/backfill, configure drafts, staff every branch, activate and place a controlled verification order before relying on notifications operationally. Vercel's existing deployment pause remains an independent release blocker.

Rollback: disable branch routing to restore legacy city permissions, then revert application code if needed. Keep metadata, audit and new indexes; no destructive rollback is required. Users created with empty legacy cities will need deliberate legacy assignments if reverting, otherwise only administrators see their orders. Never delete order/customer data or routing audit records. The administrator inbox remains available in both modes.

## Verification and discovered regressions

Focused coverage checks every saved OSM alias against both JavaScript and the historical MongoDB expression, plus unique area ownership, unknown/other-emirate fallback, administrator visibility, staff isolation, current push recipients, audited correction, concurrent configuration edits, idempotent confirmation, last-staff protection and repeatable metadata backfill. Unit, API/security and disposable MongoDB/payment regressions run without production connections or provider sends.

Browser coverage exercises setup and branch assignment at 360/390/768/1280px, current-role login, live attention counts, opt-in sound, address-review filtering, confirmation/packing, denial of another branch's order and administrator correction preserving the original address. Run the multi-account routing scenario in its own fixture session (`playwright test tests/e2e/order-routing.spec.ts`), separately from the existing admin batch: the real retained ingress deliberately limits the gateway IP to ten logins per fifteen minutes. Do not relax production limits to accommodate a combined synthetic run.

Broader checkout verification found a pre-existing frame/React-commit focus race in the mobile review step. Focus now waits for the committed stage rather than a frame scheduled before its heading exists. Existing focus regressions cover this without changing prices, payment state or order writes. A stale stock-error assertion was updated from a paragraph-specific selector to the already-existing semantic alert. The independent hosting ingress/gateway aggregate quota strategy remains unchanged.
