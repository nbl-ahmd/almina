# Intelligent search implementation — 2026-10-27

## Audit and implementation plan

The storefront calls retained `/api/products/search`, which uses an escaped regex across six fields and then image/stock/featured ranking. Autocomplete calls `/api/v1/growth/suggest`, backed by `catalog_search_terms`, prefix regex and application edit-distance scoring. `SearchBox` already has 220 ms debounce, cancellation, combobox keyboard navigation, device-local recents and English/Arabic labels. Product families are grouped in compatibility reads. Public visibility includes missing legacy flags, excludes explicit disabled/unpublished/inactive/archived products, restricts retail audience, and joins current visible categories. Product `productType` means general/otc/prescription/unreviewed, not cleanser/diaper; form, packLabel, summary and verified ingredients already exist. Existing analytics are consented coarse counters that deliberately exclude queries and product identities.

Implement incrementally:

1. Shared strict search/configuration contracts, normalization, curated vocabulary and deterministic intent.
2. Isolated Atlas provider, reproducible lexical/vector indexes, current-document policy revalidation, bounded relevance candidates, family grouping, facets and deterministic hybrid/business ranking.
3. Full result and lightweight suggest endpoints, retained endpoint routing under a rollout flag, fail-closed exact-identifier fallback. Preserve legacy provider for rollback until live Atlas verification.
4. Additive reviewed enrichment, safe seed/backfill/index tooling, offline embedding provider/jobs and cache-first query vectors. No request-time external AI/embedding generation.
5. Anonymous consented search attribution through impression/click/cart and server-confirmed purchase, TTL retention and thresholded aggregate analytics/signals.
6. Small admin synonym/rule/enrichment/test/analytics surface within current authentication architecture; storefront grouped suggestions, interpretation/correction/recovery UI.
7. Offline regression/contract/policy tests, opt-in Atlas validation, relevance/latency benchmark, E2E and running Next.js verification.

## Safety and deployment boundaries

No production data, indexes, configuration or deployments are changed by development/test runs. Index/backfill/seed/embedding scripts default to plans; explicit apply uses the existing API database configuration. Seed inserts never overwrite staff records. No legacy collection is dropped. Search remains on the legacy provider until Atlas indexes/backfill and opt-in staging checks are verified, then `SEARCH_PROVIDER=atlas` routes shopper search through the new provider. Rollback is `SEARCH_PROVIDER=legacy`; additive fields/indexes remain for investigation.

Semantic cold-start constraint: the brief prohibits generating query embeddings during shopper requests. Therefore query vectors must be prepared offline (curated seeds plus consented TTL queue). A previously unseen phrase immediately receives lexical/synonym/intent/relaxation results and becomes eligible for vector retrieval after the offline job. This is an explicit behavior, not a synchronous embedding fallback.

Live M0 latency, Atlas index acceptance and multilingual relevance must be measured against an explicitly configured staging Atlas cluster; memory MongoDB cannot execute `$search`/`$vectorSearch`. Offline timings are not Atlas performance evidence.

## New architecture and boundaries

`modules/search` owns query processing, configuration, Atlas query construction, reviewed enrichment, offline embeddings, policy validation, ranking, serialization, analytics and routes. `SearchProvider` in `search-types.ts` is the application boundary. `SearchService` combines retrieval, interpretation and response metadata; the storefront does not construct MongoDB/Atlas operators. MongoDB `products` remains authoritative; no second catalogue datastore or new search dependency was introduced.

Native Atlas provides exact token lookup, full text, phrase matching, bounded fuzziness, autocomplete and vector nearest neighbours. Application-owned logic covers vocabulary, intent, staged relaxation, safety, family grouping, curation and commercial tie-breaking. There is no new application edit-distance engine. Public query pages retain noindex, existing product/category identity URLs, responsive layouts, sort/filter controls, abortable 220 ms autocomplete and device-local recent searches.

`productType` retains its existing pharmacy classification. `searchEnrichment.productKind` separately represents consumer catalogue kinds such as cleanser/diaper. This avoids changing an existing clinical-policy field's meaning.

## Additive product representation

- `searchEnrichment`: reviewed arrays (`aliases`, `searchKeywords`, `concerns`, `useCases`, `features`), consumer product kind, age/audience and body area, provenance (`curated`, `verified`, `ai-draft`), review flag and version. AI drafts cannot be marked reviewed by this contract.
- `searchEnrichmentAudit`: staff actor and timestamp. `searchMetadataRevision` prevents a concurrent metadata edit being overwritten by a batch job.
- `searchDocument`: deterministic normalized name/brand/pack, current category name and approved merchandising metadata. No stock or price copy. Missing metadata is backward compatible.
- `searchEmbedding`: vector, model, version, updatedAt and semanticTextHash. Semantic text comes from catalogue name/brand/category/form/pack and reviewed metadata; it excludes prices, stock, customer information and invented clinical facts. Stock/price-only changes do not change its hash.
- `searchSignals`: decayed, bounded popularity/conversion plus update time, prepared offline from anonymous search events. Missing signals are neutral and old signals decay at query time too.

Clinical concerns/use cases/features require reviewed general-sale products. AI content stays draft until a separate curated/verified review. Staff cannot change price or stock through enrichment endpoints. Jobs guard the source update timestamp and metadata revision, batch at at most 200 products and emit resumable cursors. No existing field, collection, image or historical order is removed.

## Index definitions and M0 budget

Executable definitions: `apps/api/src/modules/search/index-definition.ts`. Human-reviewable snapshots: [products_search.json](search/products_search.json) and [products_vector.json](search/products_vector.json). `search:index:plan` prints the current environment-specific definitions without connecting to a database. Snapshots use default names and 768 dimensions; the executable definition is authoritative for overridden configuration.

The lexical index has explicit mappings, English/standard and Arabic analysis, name/brand/alias edge-gram autocomplete, raw exact identifier tokens, normalized name/pack text and stock/price/category/publication filters. There is one synonym mapping. The vector index has one cosine vector and filters for classification, content review, audience, category, stock, model and version. Both operate on the same products collection.

MongoDB currently documents a three-index budget across search/vector on Free clusters, a 3 KB index-definition limit, and one synonym mapping per M0 index. The initial 2,566-byte compact lexical JSON was rejected by the live M0 definition-size validator. Omitting redundant per-field `lucene.standard` defaults preserved analysis behavior and the live cluster accepted the smaller definition on 2026-10-27. Both lexical and vector indexes reached READY/queryable. Compact JSON size alone is not an acceptance guarantee. Existing indexes elsewhere in the deployment can consume remaining capacity.

## Synonyms, curation and navigation

`search_synonyms` holds staff-facing, strictly validated documents: key, type, inputs, outputs, enabled and locale. Supported types are equivalent, one_way, customer_language, brand_alias, category_alias and product_type_alias. Equivalent mappings expand in both directions; other mappings are explicitly directional. There is no milk-to-formula equivalence or automatic medical transliteration.

`search_synonyms_atlas` is a separate derived source containing only valid native `equivalent`/`explicit` Atlas documents. Disabled entries are absent from that source; no invalid placeholder mapping is written. This collection is vocabulary, not another product database. Seeding uses setOnInsert for staff-facing records and projects actual current enabled records, preserving edits/disables. Atlas synonym changes are eventually visible; validate before enabling new vocabulary in production.

`search_rules`: exact normalized query, key, type (pin/boost/hide/navigation), target product or local route, bounded boost/position, enabled and start/end timestamps. Pins and boosts only affect retrieved, visible candidates and cannot cross relevance tiers. No regex patterns or arbitrary MongoDB operators come from staff/public JSON. Hides apply to results, autocomplete and alternatives. Navigation rules accept local commerce destinations only.

Published brand/category/collection CMS pages are integrated using existing routes, including existing brand landing pages. Current public categories can be suggested even when no product name matches the autocomplete prefix. Cached navigation metadata is rechecked against current category/page publication state before use. Ambiguous queries produce navigation suggestions rather than forced redirects.

## Public API contract

All API responses use the existing `{data, requestId}` envelope and no-store policy.

- `GET /api/v1/search`: q (1–80 characters with a letter/number), locale, bounded page/limit or offset, category, brand, form, size, audience (age/consumer metadata, distinct from authorization audience), bodyArea, concern, feature, inStock, minPrice, maxPrice, featured, stock (retained exact-stock filter), offers, sort, literal and groupFamilies. Unknown fields/operators and out-of-bound pagination are rejected. Maximum candidate horizon is 300; default page size is 30.
- Response: searchId, original/normalized/interpreted query, deterministic interpretation, optional advisory correction, relaxed/unavailable flags, explicitly projected product records, category/brand/collection navigation, related queries, safe similar-product links, bounded facets and pagination. Raw scores, embeddings, enrichment, commercial signals, suppliers and wholesale audience configuration are excluded.
- Facet scope is explicitly `bounded-relevant-candidates`. Counts and price ranges describe current validated candidates and family representatives, not an unbounded estimate of the entire catalogue. There are at most 20 buckets per facet.
- `GET /api/v1/search/suggest`: distinct lightweight autocomplete; at least two characters, at most eight products and three entries per navigation/query group. It never runs vector search. The browser panel shows a compact subset with group labels, loading/failure status and keyboard options.
- Next BFF: `/api/search/suggest`, `/api/search/events`; results are server-rendered through `lib/server/search.ts`.
- Retained `/api/products/search` routes through the same service when Atlas is enabled, preserving bounded offset/limit and grouping behavior. Existing `/growth/suggest` retains its old row shape through native autocomplete. The administrative search-index endpoint refreshes additive search metadata under Atlas.

When Atlas is unavailable, autocomplete returns an explicit unavailable response, results recover safely, and an indexed exact SKU/barcode/GTIN equality lookup can still return the requested visible product. No Atlas-outage path starts an unbounded regex scan. Existing category/detail navigation is independent of Atlas. The legacy provider is an explicit rollout/rollback choice rather than a hidden outage fallback.

## Ranking and relaxation

Field weights, fuzzy bounds, timeouts, candidate counts, RRF k, semantic threshold and boost caps live in `config.ts`.

Retrieval/ranking tiers:

| Tier | Meaning |
| --- | --- |
| 0 | Raw exact product identifier/barcode/GTIN |
| 1 | Normalized exact product name |
| 2 | Exact brand plus consumer product kind |
| 3 | Strong name phrase |
| 4 | Atlas strict token retrieval |
| 5 | Directional/Atlas synonym retrieval |
| 6 | Bounded native fuzzy retrieval |
| 7 | Reviewed semantic retrieval |

Within a tier, reciprocal rank fusion combines lexical and semantic ranks with k=60. Raw Atlas text and vector scores are not added. Current stock, featured/sale status, actual photo availability and derived signals contribute at most 0.05. Pins are within-tier and only for already eligible candidates. Explicit price/name sorts remain user-controlled. A `cheap` intent prefers lower price within a relevance tier, so a cheaper semantic competitor cannot displace an exact match.

Fuzziness never operates on identifier fields. Short vitamin terms such as B12 remain catalogue language rather than being assumed to be SKUs; raw identifier equality still receives protected precedence. Numeric strength/size tokens are exact constraints during fuzzy retrieval. Normalized searchable name/pack text handles `500ML`, `500 ml` and joined name/strength formatting. Brand correction is advisory and requires an actual Atlas brand highlight; a generic product-form typo does not cause a fabricated brand correction.

Zero results trigger controlled, bounded stages: remove a size token, retain brand + kind, then retain kind. Filters such as requested category/price/availability remain. Relaxed results must be reviewed general-sale products and the UI explains the changed query. Explicit identifier and literal searches are not relaxed. Similar-product discovery also requires current general-sale review and verified family/kind/form/category; it never claims therapeutic equivalence. Valid family identity and strength are respected, with at most 60 visible option-count metadata.

## Embedding architecture and jobs

`EmbeddingProvider` separates model access. The Gemini adapter uses a fixed provider origin, secret header, explicit retrieval document/query tasks, finite dimensions, normalization, bounded retries and timeouts, with redacted errors. Only offline scripts call it.

Query vectors live in `search_query_vectors`, keyed by normalized query + locale, model/version, with a seven-day TTL. Curated seeds are prepared offline. Consented new phrases enter `search_query_queue` in **review** state; an administrator can approve a phrase through the search console, after which the offline query job processes it. Unreviewed shopper phrases are not automatically sent to an external provider.

Semantic retrieval is selective: sufficiently long natural-language/weak lexical queries with a prepared vector, no exact identifier, and no strong exact brand/kind result. It is bounded to 160 ANN candidates/30 retrieved vectors, requires an Atlas vector score threshold of 0.78 on the cosine index, and revalidates current filters, reviewed general-sale classification, semantic-text hash, current model/version and verified brand/form/age/body-area/concern/feature constraints. Empty/low-confidence/missing-model/stale vectors contribute nothing. Model/threshold quality still requires staging measurement. New unseen or unapproved phrases continue immediately through lexical/synonym/intent/relaxation retrieval until their vector is prepared.

Product embedding jobs regenerate only changed semantic hashes/model/version/dimensions in missing mode; rebuild mode explicitly regenerates a batch. Source changes during processing cause a guarded update to skip, and a later pass can retry. Check returned cursors and repeat bounded batches. For a model/dimension change, disable semantic retrieval, rebuild embeddings and the matching versioned vector index, verify, then enable it; do not mix incompatible model spaces.

## Analytics event schema and privacy

The existing coarse `commerce-events` contract and its consent promise remain intact. Search improvement reporting requires both existing usage consent and a separate new search-reporting opt-in. Existing users are not silently opted into query/product reporting. DNT/GPC override both. Browser concurrency/rate are bounded, impressions are visibility-batched, pending sends abort on withdrawal, and optional storage/network failures never block shopping.

`search_sessions` initially stores only a random searchId, query hash/length, intent type names, locale, result membership/positions, count and flags, expiring after one hour. With explicit search consent, eligible normalized query text and anonymous event flags may remain for seven days. Obvious email/phone/contact/identity patterns are excluded from retained query text. No customer/account/IP/cookie/order identity is copied into analytics.

Client event contract: `{searchId, event, items:[{productId,position}], query?, locale?, previousSearchId?}`. Events are search_performed, search_result_impression, search_result_clicked, search_add_to_cart, search_checkout and search_exited. The server checks current context, membership and position and deduplicates by searchId/event/product. Previous search IDs are used only to derive a short-window reformulation flag and are not stored as customer histories. Exit reports are best effort on pagehide without an interaction, not a guaranteed complete measure of every browser shutdown.

Checkout may carry bounded optional searchAttribution rows `{searchId,productId,position}`. The server verifies consented, unexpired result membership and actual purchased products. Successful purchase events and authoritative line revenue commit in the existing order transaction with opaque deduplication receipts; no order number or customer data is copied to them. The commerce fingerprint excludes optional attribution, so retries/withdrawal cannot change order pricing, stock behavior or replay identity. Failed orders produce no purchase events.

Events expire after thirty days. Thirty-day daily query aggregates retain hash/counts and only approved vocabulary labels. Public popular queries require at least ten searches and approved vocabulary; no raw personal search history is published. Reports include top/zero/low-CTR/converting queries, first-result CTR, search usage, click/cart/checkout/purchase rates, attributed revenue, reformulation and best-effort exit rate. Popular counts have UTC-day 24h/7d/30d windows; the 24h field is a day-bucket approximation. Revenue is attributed committed line revenue (including applicable line tax, excluding shipping), not a finance ledger. Purchase metrics count accepted orders, not a net-of-refunds accounting report.

The storefront privacy description and separate consent control explain these practices. Anonymous signal aggregation uses decay and a cap; no order query runs on a shopper search request.

## Administrator tooling

`/admin/search` uses the existing admin shell, session cookie, BFF policy and server-side admin role checks. It provides synonym/rule list, edit and disable controls; a compact advanced schema editor; reviewed enrichment; a search test console with tier, matched fields, lexical/vector rank, RRF, boosts and timing; query approval for the offline job; and selectable analytics reports. This is intentionally a small settings surface, not another CMS.

API routes: GET `/api/v1/admin/search`, GET `/api/v1/admin/search/test`, POST `/api/v1/admin/search/{synonyms,rules,enrichment,query}`. All mutations require admin authentication and browser-origin/CSRF checks; unknown body fields/operators are rejected. Public shoppers cannot request explain output.

## Deployment steps — prepared, not executed against production

1. Review changes and deploy the API/BFF code together with `SEARCH_PROVIDER=legacy`. Verify current storefront/admin/checkout behavior. Keep the rollback version available.
2. Use a dedicated staging Atlas catalogue and existing validated database configuration. Inspect current Search/Vector index capacity. Run plan commands first.
3. `npm run search:synonyms:seed` prints a plan; append `-- --apply` to seed without overwriting staff edits.
4. `npm run search:backfill -- --apply --limit=100`; repeat with the emitted `--cursor=<id>` until null. Review malformed/unreviewed catalogue metadata before marking it approved. This never changes prices, stock or publication.
5. `npm run search:index:plan`, then `npm run search:index:apply`. Search index builds are asynchronous. Run `npm run search:index:verify` and require both indexes READY/queryable before enabling Atlas. Do not treat submission as success.
6. Inject the offline embedding secret. Run `npm run search:embeddings:missing -- --apply --limit=100`, resume with cursors, and run `npm run search:embeddings:queries -- --apply`. Rebuild has a separate explicit command. No command generates embeddings unless apply is supplied.
7. Set explicit staging test settings; `npm run search:test:atlas` with SEARCH_ATLAS_TEST_ENABLED=true must run (not skip), and `npm run search:benchmark -- --atlas` must be evaluated on a fixture-equivalent staging catalogue. Verify English/Arabic, typo, stock/price updates, categories, curation, semantic thresholds, no-index/outage fallback and M0 resource use. Regular tests do not require Atlas/internet.
8. Enable SEARCH_PROVIDER=atlas in staging, then after a reviewed production rollout. Enable semantic retrieval only after model/index/hash/query-cache verification. Enable analytics only with the deployed separate consent UI and collector configuration.
9. Schedule the offline missing-embedding/query-vector jobs and `search:signals -- --apply` using the existing job runner; choose a measured cadence (for example hourly query preparation, daily signals). Process only reviewed queue entries. Jobs are bounded; monitor cursors and failures rather than assuming a single batch covered the catalogue.
10. Observe p50/p95/p99, result quality, zero rates, current-price/visibility changes, resource usage and errors. Initial targets: autocomplete p95 below 300 ms; lexical p95 below 500–700 ms. These are targets, not measured production claims.

## Rollback and legacy retirement

Set SEARCH_PROVIDER=legacy and SEARCH_SEMANTIC_ENABLED=false, then restart the affected services using the normal release process. If needed disable SEARCH_ANALYTICS_ENABLED as well. Additive fields/collections/indexes can remain inert for investigation; rollback requires no data restoration and does not change orders, prices, stock, media or URLs.

The old `catalog_search_terms`, editDistance/searchScore functions, regex listing and token-index schema remain explicitly deprecated as a rollback path. Under Atlas, storefront search, retained suggestions and the batch endpoint use the new path. Nothing is dropped during rollout. Retire the old engine/collection/index only after staging and production acceptance, external compatibility review and a separate cleanup change.

## Tuning recommendations

Measure real Atlas relevance/latency before changing weights, threshold, dimensions or candidate limits. Expand reviewed bilingual vocabulary and verified general-sale metadata from zero-result reports. Tune at the provider/configuration boundary with the golden dataset. Consider Atlas search-after pagination beyond the current explicit 300-candidate horizon only when needed. M0/Flex/M10/Search Nodes share the same provider/API; changing the infrastructure tier does not require another product database or a rewrite.
