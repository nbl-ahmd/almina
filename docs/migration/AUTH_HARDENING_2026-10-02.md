# Authentication and authorization hardening

Implemented locally on `codex/auth-hardening`, 2026-10-02. This covers **both** the deployed-contract legacy service and the additive TypeScript API, with compatible legacy admin callers. No deployment, production database access, account changes, index application, credential rotation or history rewriting was performed.

The complete [route authorization matrix](AUTHORIZATION_MATRIX_2026-10-02.md) inventories 53 legacy handlers plus versioned API routes, Next pages/actions, static delivery and Socket.IO. Regression tests compare the actual Express route inventory with the default-deny allowlist so a new handler cannot silently become public.

## Audit findings and remediation

| Finding | Implemented control |
|---|---|
| Hardcoded, unexpiring JWT signing secret; browser localStorage token | JWT implementation/dependency removed; no bearer/JWT fallback; host-only cookie with server-managed opaque session |
| Embedded MongoDB, Google service-account, WhatsApp, SMTP and VAPID credentials | Source copies removed, rotated credentials must be injected; no credential values in this report |
| Public signup accepting arbitrary roles | Existing signup URL becomes server-authorized admin provisioning; only known roles; no public staff registration |
| Unprotected staff listing/deletion; password/subscription leaks | Admin checks before handlers; allowlisted staff projections; bounded/keyset user listing; self-deletion denied; session revocation on deletion |
| Product/create/edit/delete/publish, category/banner/store/batch mutations public | Explicit admin policy at the mounted API boundary before body/upload/handler work |
| Public order PII and administration; city filtering only in browser | Database city scope on staff list/detail/dispatch/cancel; general editing admin-only; empty assignments grant no access |
| Guest order creation can choose admin flags/identifiers | Only customer/cartItems accepted at top level; server assigns identifier and initial flags; financial algorithms remain a separate critical finding |
| Public messaging/recipient/conversation/poster administration | Admin policy for every management route; published poster image downloads remain public to preserve Meta/shared-image contracts |
| Public push callback trigger, unowned subscriptions | Staff authentication; store/delete only current user's subscription; HTTPS push-provider allowlist and bounded keys/endpoints; no caller-selected user writes |
| Login enumeration/abuse | Generic credential/session error; asynchronous bcrypt including dummy comparison for unknown/invalid accounts; strict input/UTF-8 byte limits; IP/account quotas |
| Missing session invalidation | Absolute expiration, logout, logout-all, re-login rotation, current-user/role/city lookup and password fingerprint check |
| Wildcard CORS, no CSRF boundary | Exact configured origins, credential CORS, custom header + mandatory Origin for state changes; cross-site Fetch Metadata rejected; no Origin fallback |
| Anonymous realtime customer/message broadcasts | Exact-origin admin-only handshake; current identity verified before every outbound event; revoke/expire/demotion disconnects |
| Unsigned/replayed WhatsApp webhooks | Constant-time raw-body HMAC-SHA256 validation, configured provider secret, durable unique event receipt before effects |
| Arbitrary Mongo filters / regex inputs | Legacy compatibility filters reconstructed from typed allowed fields; caller operators rejected; bounded literal search escaped on server |
| Unbounded administrative uploads | Authorization before parsing; image file/count/field limits, MIME filter, Sharp content decoding with 20-million-pixel limit; bounded CSV upload |
| Public email relay and insecure SMTP TLS | Relay admin-only; checkout confirmation sent internally from persisted order to its stored recipient; verified SMTP TLS; no browser HTML/destination submission |
| Missing/weak document and API security headers | Restrictive API CSP; fresh-nonce Next CSP; frame denial, nosniff, referrer/permissions policies, environment-aware HSTS; legacy static-host configuration provided |

Credential copies formerly tracked at `backend/.env` and `backend/routes/cred.json` were removed from the repository. That material is **compromised/untrusted and must not be reused**. The code no longer auto-loads those files. Git history and any prior copies still contain exposed credentials; deleting current files does not revoke them. ## Sessions and trusted permissions

`backend/security/sessions.cjs` is the shared session implementation. It follows the retained service's CommonJS convention, with a declaration file for the TypeScript API. Neither import connects a database or loads an environment file. `apps/api` bundles the module into its isolated production artifact; it never imports legacy startup, Mongoose, providers or legacy configuration. Both services use their own injected database handle and the same production-compatible `users`/`api_sessions` collections when configured to the same database.

A successful bcrypt login generates 32 random bytes (256 bits) encoded as an opaque token. Only SHA-256 token digests, user IDs, expiration, scheme marker and a password-hash fingerprint are stored. Tokens are returned only through `Set-Cookie`, never through a browser-readable JSON field. Sessions expire after eight hours without renewal. The server checks expiration itself; TTL cleanup is housekeeping. Login rotates the current browser session; logout deletes its digest; logout-all removes all sessions for that user. Password-hash changes invalidate all prior sessions without destructive user migrations. Each authorized request reloads the user: deletion, disabling, role or city changes apply on the next request. Legacy JWTs and pre-hardening bearer sessions are deliberately rejected; operators and staff must reauthenticate.

Production/staging cookies use `__Host-almina_session`, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, with no Domain attribute. Only explicit development mode uses the insecure loopback cookie `almina_session`. No automatic fallback based on forwarding headers or TLS detection. Default proxy trust is off; configure only explicit ingress IPs, with ingress overwriting forwarding headers. Neither service accepts a role or identity from the request body, Authorization header, localStorage or a cookie payload.

Existing bcrypt documents remain readable (cost 4–14, validated hash format); new provisioned passwords use bcryptjs 3.0.3 at cost 12 and must be 12 characters to 72 UTF-8 bytes. Unknown usernames, wrong passwords, malformed/unsupported hashes, unknown roles and disabled users receive generic failures. The dummy hash is synthetic, not an account credential. Old varying bcrypt costs can still have timing differences; generic responses do not promise perfect timing indistinguishability. Rehashing existing production credentials and MFA remain separate, reviewed work.

**High-risk rollout assumption:** the two legacy roles represent approved staff. The former public signup allowed arbitrary admin creation, so the current account/role/city inventory is not inherently trustworthy. Operators must verify approved accounts, disable/revoke unauthorized identities and review old hashes before enabling production login. No user documents were inspected or changed here.

## Origin, CSRF and abuse controls

All cookie-authenticated POST/PUT/DELETE operations, login, guest checkout and the legacy cart gate require an exact allowed Origin plus `X-CSRF-Protection: 1`. Browser cross-site Fetch Metadata is rejected. The custom header forces cross-origin preflight; CORS permits only exact reviewed origins and expected methods/headers. There is no wildcard or `null` origin allowance, no permissive Referer fallback, and no exception for JSON, forms or multipart. Read-only server catalog calls may omit Origin. The signed webhook is the sole state-changing provider exception.

This is an Origin/custom-header CSRF defense rather than a token-cookie double-submit implementation. XSS is addressed separately through CSP and HTTP-only cookies; same-origin XSS could still issue authorized requests. No long-lived auth token is stored in localStorage/sessionStorage. The legacy client purges the old token, uses credentialed requests only for the configured API origin, sends the CSRF header, and checks `/auth/me` for protected routes. Cached display name/role/cities are UX hints; the server always derives permissions anew.

Per-process edge quotas are 120 API requests/minute/IP and 10 login attempts/15 minutes/IP. Validated login attempts also increment MongoDB atomic fixed-window quotas: 50/IP and 20/account per 15 minutes across service replicas, including unknown usernames. Account quota keys normalize case/Unicode to limit variant abuse without changing exact legacy login lookup; database quota keys hash identifiers; no raw usernames/IPs are logged. Quota storage failure fails closed. Additive TTL indexes clean old windows. Shared edge/global quotas and upstream ingress limits remain necessary for high-volume distributed abuse; malformed login bodies do not enter the database quota but hit the per-process limits.

## Provider/media compatibility and limitations

- All existing API paths, document IDs, order history and media files are retained. Privileged callers now require cookies and provenance; cookie rollout must coordinate the admin client and backend. Legacy public order reads/signup/email relay are intentionally no longer public.
- Legacy admin defaults to same-origin `/api` and Socket.IO. Deploy fixed reverse proxies under the storefront origin; otherwise a reviewed same-site API origin also needs matching CSP media/connect directives. Unrelated registrable domains are incompatible with the Lax/cross-site policy. Do not weaken cookie/CSRF rules to preserve the old unrelated Render origins.
- Published WhatsApp poster image URLs remain public because the admin copies them into external templates. Listing, upload, deletion, recipients and messages remain admin-only. Public catalog/poster media permits cross-origin resource embedding; private API responses retain same-origin resource policy. Static delivery only mounts existing catalog directories, excluding source files, CSV and private administration paths. No media file was deleted.
- Realtime is conservatively admin-only because the existing event payloads are unscoped customer/message PII. Staff continue to use city-scoped HTTP order reads; staff realtime delivery needs a separately verified room/scope contract.
- `WHATSAPP_APP_SECRET` validates Meta's `X-Hub-Signature-256` over the raw JSON bytes. `VERIFY_TOKEN` still handles provider verification GET. Signed incoming message/status receipts have unique IDs, and duplicate effects are rejected. Current legacy handlers consume one entry/change/event; multi-event batches are rejected rather than silently partially processing them. **Receipt-before-processing is at-most-once, not transactional exactly-once delivery.** Processing failures after receipt insertion require reviewed operator recovery; no automatic delete/replay is performed. Retention/load and real provider batch/retry behavior require staging verification.
- WhatsApp uses injected `WHATSAPP_ACCESS_TOKEN`; Google Drive uses external `GOOGLE_APPLICATION_CREDENTIALS`. Provider APIs, folder IDs and media references remain compatible. Provider exceptions/request bodies no longer print credentials or customer payloads.
- Checkout confirmation uses the existing SMTP provider with injected `SMTP_USER`/`SMTP_PASSWORD`, verified STARTTLS and a simple server-owned text message. Failure is isolated after order persistence, logs only a static failure, and cannot corrupt an order. There is no durable mail queue/retry yet; notification delivery and final template parity need staging verification.
- Push subscriptions are saved/deleted on the current staff account, not used as arbitrary immediate callback destinations. The old demo notification trigger is removed. The native service worker preserves standard Web Push and FCM-shaped notification envelopes without loading remote scripts or unused Firebase SDK/token configuration. Current application sources had no Firebase `getToken` caller or backend Firebase sender. Rotated `REACT_APP_VAPID_PUBLIC_KEY` is public configuration; absent configuration disables automatic subscription attempts. Server push delivery/jobs remain separate from secure subscription management; current order alerts use authenticated realtime.

## Security headers

Both API services emit `default-src 'none'`, `frame-ancestors 'none'`, restrictive base/form directives, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, and no-store responses. HSTS is enabled outside explicit development mode for HTTPS deployments, without includeSubDomains or preload assumptions.

Next.js 16.3.8 bundled CSP/Proxy documentation was read before edits; the registry recheck still lists 16.3.8 as the latest stable 16.x release. No framework upgrade was needed. A fresh per-request nonce authorizes framework scripts and style elements. Production script policy has neither unsafe-inline nor unsafe-eval, nor third-party script hosts. Development alone permits unsafe-eval for React diagnostics. Image sources include the CDN and exact validated legacy media origin. `style-src-attr 'unsafe-inline'` supports generated Next image style attributes and does not authorize scripts. Root layout waits for a request; document responses are private/no-store, deliberately disabling static/ISR HTML reuse with nonce CSP. Frame ancestors are denied; staging/production HTTPS gets HSTS and upgrade-insecure-requests. No third-party scripts were added to make CSP pass.

The CRA build externalizes its webpack runtime, uses a self-hosted-script CSP in the document, and removes third-party tracking/icon/bootstrap scripts. Its existing bundled React Bootstrap/Remix/MUI stack remains. Existing external CSS/font hosts are explicitly scoped; inline styles remain necessary for MUI/React in this legacy app. A meta CSP cannot enforce frame-ancestors or HTTP-only response headers: apply [the reviewed static-host header configuration](legacy-security-headers.nginx.conf) on the **actual** document host. Hosting is not verified and no configuration was deployed. Do not claim production document headers are enabled merely from this source change.

## Additive data/index plan and rollback

No existing user/product/order data, hashes, totals or inventory was migrated. Session and quota documents are additive. `User.subscription` corrects the old schema typo without backfill/removal. New index plan entries are `api_sessions.userId` and TTL `auth_rate_limits.expiresAt`; the existing unique token digest and expiry TTL indexes remain. Webhook receipts use MongoDB's unique `_id` index. Runtime does not build indexes.

`npm run db:indexes:plan` is connection-free and was executed. `--apply` was **not** executed. Verify actual `users.username` uniqueness/duplicates and the session indexes against sanitized staging, then review/apply the existing additive idempotent migration with explicit environment/name/URI controls. Runtime needs only necessary collection permissions; index-management credentials should be separate.

Rollback retains additive collections, historical data and indexes. Never roll back to the public admin routes, compromised JWT secret, token localStorage or insecure relay. Revert isolated UI/provider changes only while keeping the auth boundary and Origin protections. Retain new session scheme markers; old bearer/JWT sessions must not regain access. Keep approved accounts and rotated secrets. Nothing requires dropping collections or deleting customer/order data.

## Verification and remaining production gates

Local regression tests exercise real legacy routers on loopback plus versioned API HTTP, synthetic database/query doubles and provider doubles. They prove anonymous denial for every privileged route, staff denial for every admin policy, role/city scoping, forged role rejection, protected user listing/deletion, guest administrative-flag rejection, cookie flags/token omission, Origin/CSRF/multipart rejection, login quotas across service instances, generic credentials, session rotation/expiration/logout/password/deletion invalidation, scoped push ownership/deletion, signature/body-tamper/replay rejection, public media compatibility and realtime reauthorization. No MongoClient connection, production account, provider request or commerce-data mutation was involved.

Checks performed: full workspace typecheck/lint; **107 automated tests passing**; API bundle and Next Turbopack production build; CRA production build (existing warnings remain); compiled API/foundation/storefront smoke (including fresh nonces on every response, caller nonce override rejection, nonce on every framework script and no production unsafe-eval/unsafe-inline scripts); connection-free index plan; running Next MCP route/compilation/error diagnostics; desktop/mobile storefront navigation/reload/cart/error recovery; production-mode image loading, hydration/cart actions and CSP blocking of inline event handlers; real CRA login with forged-localStorage denial, HTTP-only cookie, refresh persistence and server revocation on logout. Fixtures are restricted to loopback and use synthetic accounts/catalogs. A React development performance-measure warning during intentional outage testing cleared on fresh navigation; normal MCP diagnostics were clear.

Production gates: rotate/revoke exposed credentials and review history/access; inventory and approve staff roles/cities; verify indexes and real database concurrency; configure TLS, exact origins, proxy trust and same-origin routing; apply/verify static document headers; test real uploads, WhatsApp signatures/batches/retries, SMTP and push lifecycle; verify deployment/start commands and Node 24 legacy runtime; confirm monitoring, multi-replica ingress limits and recovery. These are operator/staging evidence requirements, not completed production actions.

**Unresolved critical commerce risk:** guest checkout still trusts client financial values, decrements stock unsafely and lacks atomic/idempotent order creation. This change restricts authentication/administration and prevents guest administrative-field injection; it does not make the legacy checkout production-safe. That work remains the next migration priority. Legacy dependency advisories, old hash strength, unbounded legacy collection reads, media parity and durable provider jobs also remain documented work.
