# Maintained outbound WhatsApp

Replaces the unbounded Axios helper and hard-coded v17/account with a maintained fixed-origin native-fetch sender. Requires server-only WHATSAPP_ACCESS_TOKEN, WHATSAPP_API_VERSION and WHATSAPP_PHONE_NUMBER_ID; no default guesses or account registration/migration occur. The operator must confirm a supported version and the existing production phone identity before promotion. [Meta's official message collection](https://www.postman.com/meta/whatsapp-business-platform/folder/13382743-ba8d099d-007e-4b52-b9f2-3cf3c60e4fbc) specifies the version/phone-number messages endpoint. Text and existing en_US image-header template contracts remain. Imports/builds do not read credentials or send messages. Axios and the unused helper are removed.

Sender limits: ten-second send/body deadline, 64-KiB acceptance body, four concurrent operations, no redirects or automatic retries. A transport ignoring abort keeps its slot. Input/config/provider failures are redacted. Only a bounded JSON acceptance containing one provider message identifier succeeds; acceptance is never represented as confirmed delivery.

whatsapp_outbound is an additive majority-written actor/key/digest-bound receipt. Exactly one insert owns the provider attempt. Sending/uncertain receipts cannot resend automatically, including after crashes. Accepted receipts can finish a failed database transaction without another provider call. Conversation history and completed receipt commit together under the same inbox serialization control; realtime emits only after commit and preserves the authorized existing event contract. Existing conversations/opt-outs/messages/IDs remain. New conversations created by an accepted administrator reply default to promotions disabled. Templates never fabricate conversation text or delivery records. Existing recorded opt-outs are enforced even for CSV recipients; approval for otherwise unrecorded recipients and Meta's messaging window/template rules require operator/provider acceptance. An opt-out after provider submission cannot retract that in-flight send.

Retained /s success JSON and /text acceptance redirect remain. An optional Idempotency-Key expands the compatibility contract; old callers without it receive a new receipt for each request and have no cross-request retry guarantee. Next single-text/template and bulk forms always submit a saved receipt key through the independently authorized gateway. A private tab session stores bounded opaque keys and SHA-256 request fingerprints, without plaintext numbers/content. Fingerprints are still private personal data, not anonymous analytics, and must never be logged/exported. Identical sends survive reload; changed input has a new key. Storage corruption/unavailability/capacity fails before sending, and uncertain entries are never evicted automatically. Closing the tab or changing input starts a new intent; review delivery reports before doing so. A separately approved repeat campaign must not reuse an old intent accidentally.

The unused movie-demo root sender and fake-success /sr are retained as authenticated explicit 410 URLs, with tests proving no provider effect. No active Next caller uses them. Production external-caller inventory must confirm this retirement before promotion.

Tests: configuration/payload/response bounds, outage/no retry, stalled body cancellation, ignored cancellation, private retry storage/reload/input binding; mandatory disposable MongoDB accepted-then-failed-commit/concurrent retry, unknown acceptance, changed payload, opt-out, unchanged conversation and retained HTTP/RBAC/demo parity. Browser coverage exercises keyboard, accepted reload retry and uncertain no-resend/no-fabricated-history at 360/390/768/1280px. Synthetic fixtures only; no real provider sends or customers/orders were fabricated.

Local validation: lint/typecheck; 78 unit, 104 API/security, 40 mandatory disposable MongoDB/load and seven release-gate tests pass, isolated Next/API foundation build and both remaining lockfile audits pass. All 34 existing compiled browser cases plus eight new WhatsApp cases pass (38-case full run followed by eight-case focused verification). Single/bulk sharing and corrupted storage are checked at every required width. A test-only combined four-width session reached the real rate limit; splitting independent viewport cases preserves that security boundary rather than disabling quotas. Running Turbopack MCP reports no compilation/config/session errors; agent-browser shows Server(AdminPage), the interactive AdminForm, accepted history and reload retry with exactly one provider call/receipt/message. The provider in this runtime check is injected synthetic; Meta was not contacted.

Rollback retains the expanded receipt fields/collection; never deploy the old sender over an unresolved receipt or retry uncertain sends. Provider reconciliation must use actual Meta identifiers/reports before an explicit operator decision. Store recovery remains closed. Persistent-service consolidation, push delivery, client telemetry/component work and hosted acceptance remain gates.
