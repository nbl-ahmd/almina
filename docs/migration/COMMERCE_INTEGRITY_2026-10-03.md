# Authoritative checkout and order lifecycle

Implemented locally on `codex/commerce-integrity`, 2026-10-03. No production database, deployment, credentials, stock, historical totals, or provider settings were changed.

## Approved policy

The owner confirmed VAT-inclusive catalog prices, AED 10 merchandise minimum after discounts and before delivery, free delivery in Ras al-Khaimah and AED 21 in the other six UAE emirates. VAT applies to products with the legacy `vat: true` flag at 500 basis points. Embedded VAT is rounded half up once per line using price × quantity × 500 / 10500; it is reported, never added again. Delivery fee remains the existing inclusive charge; no additional delivery tax is added. Payment choices remain `cash` and `card` on delivery. Sales use the stored `salePrice` only when `sale === true`; the saved discount is the difference from regular price. An enabled sale with missing/invalid sale price fails closed.

The owner also confirmed that new orders cancelled before dispatch restore stock once. Dispatched/refunded orders cannot be cancelled. Refund status records an administrative workflow action for delivery payments; it neither executes a financial refund nor assumes goods have been returned.

The approved policy is provisioned additively in `commerce_policies/checkout` by the migration script. Rerunning it does not replace an existing operator policy. Unrecognised emirates, a closed/missing store, invalid policy, missing counter, corrupt prices and fractional stock fail closed. Existing missing publication flags preserve legacy visibility; explicit disabled, inactive, unpublished products and disabled/missing categories are rejected. Malformed publication flags fail closed. Delivery is calculated from the selected supported emirate; this does not add address geocoding or distance pricing.

## Contract and transaction

Both `/api/orders` and `/api/v1/checkout` execute the TypeScript service in `apps/api/src/modules/orders/commerce.ts`. The legacy adapter is bundled by `npm run build:commerce`; root build/pretest build it. Startup checks a source/lockfile hash manifest and requires a current built adapter; it does not need development tooling at runtime. Direct PM2 invocations must run that build before startup. API build bundles the service itself. Root build still installs both root/backend packages and root start still runs PM2; build explicitly includes existing development tools to compile the TypeScript adapter before any production pruning. No new dependency or version upgrade was added.

The strict request contains `customer`, `items: [{ productId, quantity }]`, and a UUID `idempotencyKey`. Customer accepts only delivery/contact information and `payment: cash | card`. Every unknown field, including monetary fields on customer/items/top level, is rejected before database access. Quantity must be an integer from 1–1000; up to 100 input lines are accepted, duplicates are combined and bounded again. No browser commercial value is read. The quote endpoints `/api/orders/quote` and `/api/v1/checkout/quote` accept the same intent without a retry key, and never reserve inventory.

Each checkout transaction reads current products/categories/store/policy, calculates integer AED fils, claims a hashed retry key, conditionally decrements each product with `stock >= quantity`, increments the seeded counter, inserts the immutable order and records a notification outbox event. Any failure aborts all writes. There is no standalone-MongoDB or nontransactional fallback. All operations in a session are sequential, consistent with [MongoDB driver transaction requirements](https://www.mongodb.com/docs/drivers/node/current/crud/transactions/). Reads use snapshot isolation and commits use majority write concern. Both installed legacy driver 5 and API driver 7 are covered by actual HTTP integration tests; their transaction callback return-value differences are adapted explicitly.

The receipt collection uses its built-in unique `_id` index, containing SHA-256 of the opaque UUID key. The fingerprint covers normalized IDs/quantities and validated customer/payment data. Matching retries return the committed order and its original prices, even after catalog changes or cancellation. Reusing a key with a different intent returns 409. Receipts have no TTL: deleting them could permit old requests to create another order. Keys identify submissions rather than authenticate customers; public responses never contain customer PII or the key. There is no new public customer-order lookup endpoint.

Order numbers retain `OD<number>`. The maintenance migration scans numeric legacy order numbers once to establish the high-water mark; subsequent checkout uses a single counter document. Reruns use `$max` and never lower the counter. Checkout also makes an indexed collision check and fails closed if a legacy number already occupies its allocation. A partial unique order-number index covers schema v2; historical duplicate identifiers are preserved rather than deleted or renamed.

## Snapshots, state and compatibility

New schema v2 orders snapshot product ID, SKU (`product_id`), barcode, name, regular unit price, nullable sale unit price, discount, VAT rate/amount, quantity and line total. Totals store currency, policy version, VAT mode, merchandise subtotal, discount, tax, delivery, minimum and final amount in minor units. Commercial snapshots have no mutation endpoint. Legacy `customer` totals and `cartItems` remain as server-derived compatibility fields. Order/customer IDs remain unchanged.

States follow `pending → confirmed → packed → dispatched → refunded`, with cancellation allowed from pending/confirmed/packed only. Every transition is recorded with server time and staff identity, uses a transaction and applies current city RBAC. Refund requires admin. Repeating a status is an immutable no-op. Cancellation and dispatch races serialize through order writes; new cancellation restores each line's quantity in the same transaction, and missing/corrupt stock aborts restoration and status together. Legacy orders never infer or automatically restore historical stock effects.

Legacy dispatch URLs remain adapters: one dispatch command validates billing against the recorded order total and records the intermediate confirmed/packed states as well. Commercial order edits are rejected, and the old quantity/price editor is removed from the staff detail screen. Repeating dispatch does not rewrite billing. The browser displays the explicit server state and lifecycle errors. New line displays use snapshots even when the product is changed or missing; old lines retain current-catalog hints only with a visible provenance notice and missing-product placeholders. Stored historical totals are never recalculated.

Legacy checkout sends only intent fields, shows a live server quote for review, suppresses repeated clicks, preserves the exact request/key in session storage until a definite result, restores retry contact details on reload, and displays the committed server amount on success. Cached browser minimums cannot block a valid server quote. Definitively aborted validation/stock failures release the attempt; network/server failures retain it. Changing the cart/details during an uncertain attempt is blocked to avoid accidentally creating another order. Old browser bundles that send prices/totals are rejected and must refresh. Quote review does not freeze prices: checkout always recalculates from its transaction snapshot, and the confirmed response records that final amount.

The legacy notification worker polls a durable Mongo outbox with leases and retry backoff. SMTP/provider failures never affect committed orders. SMTP delivery is at least once; a crash after provider acceptance may duplicate email. The worker runs in the persistent legacy process and may continue draining events created by the versioned API against the same database. Keep that process running until a replacement worker is verified. No historical orders are enqueued. Realtime remains an authenticated, postcommit best-effort signal and is not a persistence boundary.

## Migration and rollout

`npm run db:commerce:plan` is connection-free. `scripts/migrations/commerce.ts --apply` requires isolated API configuration and `COMMERCE_WRITERS_PAUSED=true`. It verifies replica-set/mongos topology, applies additive indexes, backfills absent status/provenance fields in batches, seeds the counter and inserts the approved policy if absent. It never changes stock, amounts, cart lines, IDs or existing policy. Contradictory dispatched/cancelled flags become `legacy_conflict` and cannot be mutated through the state machine until reviewed. It is restart-safe through absent-field predicates, `$max` and `$setOnInsert`. Legacy fields are retained in full. Genuine historical names/prices/SKUs/barcodes were never saved, so they cannot be truthfully reconstructed from today's products; this script records snapshot provenance as unavailable.

Before rollout:

1. Back up the authorized production database and inventory legacy data anomalies/duplicate order numbers using a read-only snapshot.
2. Verify Atlas/replica-set transactions, database privileges, existing policy/store documents and proposed indexes in staging.
3. Stop **all** legacy/new checkout and order-status writers, drain in-flight requests, build the shared adapter, then apply the additive migration using explicitly injected environment settings. Do not load `backend/.env` into tooling.
4. Verify counters, index definitions, policy aliases, city assignments and counts. Resume only applications executing this shared service; an older writer would bypass these guarantees.
5. Roll out the refreshed browser bundle and verify delivery-payment billing/dispatch/cancellation, retry after a lost response, old order rendering and notification recovery with authorized synthetic staging orders.

No production migration has been run. Apply commands are intentionally operational rather than part of installation/build/test. Rollback must keep this safe shared writer or pause checkout and forward-fix. Keep counters/receipts/snapshots/outbox and all post-cutover orders; never lower a counter, delete receipts, restore a stale database over new orders, or reactivate the unsafe old checkout handler. Additive status fields can be ignored by old read-only consumers, but lifecycle writers must not revert to independent flags. No legacy fields may be removed until authenticated production parity and reconciliation are verified in a later migration.
