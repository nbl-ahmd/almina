# Transactional WhatsApp inbox

Signed webhook receipts previously committed before conversation/report writes, and processing exceptions were swallowed. A failed write could therefore discard a valid provider retry. The retained signature boundary now delegates bounded event normalization and receipt ownership to maintained TypeScript, and the existing webhook URL delegates processing to a maintained transaction.

New receipts retain a normalized event, digest, `pending` state and receive time. Conversation/report append and `processed` state commit together. Exact pending retries resume processing; processed retries acknowledge without duplicate messages/reports/events. Reused IDs with changed normalized content conflict. A small shared notification-control document serializes first-contact/report creation independently of commerce state. Existing document IDs, collections, report fields and authenticated realtime event names/payloads remain; new entries add an opaque provider event ID. Realtime emits after commit and remains best-effort; admin reads reconcile after disconnects.

Incoming ordinary text preserves an existing promotion opt-out. Explicit button responses retain their prior status value. Unsupported message media is acknowledged without inventing message text, customer identity or consent. New conversations require an actual supplied profile name; missing identity remains pending for review. Existing historical receipts without a state remain acknowledged because their effects are unknown. Do not replay them automatically or fabricate lost conversations/customers/orders.

## Verification and rollout

61 unit, 99 API/security/upload and 31 mandatory real disposable-database/load regressions passed. Fault-injected real HTTP/database tests verify failed message and delivery-report transactions leave pending receipts and no partial effects; subsequent/concurrent signed retries append once, preserve explicit opt-outs and leave order/stock data unchanged. Signature tampering, reused-ID conflicts, legacy receipts, malformed/bounded payloads and unsupported media are covered. Lint/typecheck, foundation build and all 26 Chromium regressions passed.

The webhook JSON limit remains 128 KiB, with one entry/change and at most one message or status per request, preserving the previous accepted envelope. Messages are bounded to 4000 characters, profile names to 100, delivery errors to bounded fields. Unknown provider metadata is not retained in receipts or logs. Receipts/conversations contain private communications: restrict database/admin access, protect backups and apply reviewed retention rather than automatic deletion.

Use one webhook-processing version during rollout. Old processors do not understand pending receipts and must not concurrently handle these deliveries. On rollback, pause webhook routing, retain pending receipts and replay only through this compatible processor after restoration; never run the old receipt-before-write path over pending events. Existing `from`/name indexes require production inventory: the legacy unique-name index can reject distinct contacts with the same name. Such failures remain pending and require explicit index migration/reconciliation; do not change names to evade it.

HTTP drain already awaits active webhook processing; there is no new background worker. Provider retry exhaustion, live template/API-version/credential acceptance, pending-event alerts/operator recovery, outbound sends and push/Drive adapters remain gates. No live provider call, production data migration, master merge or legacy contraction occurred.
