# Optional consented commerce reporting

This held candidate finishes the repository analytics/client-error gap. Hosting is the owner's responsibility; no production deployment, merge, provider send or data migration occurred.

`COMMERCE_TELEMETRY_ENABLED=false` is the default for both Next and Express. Enable it on both services to display equal Allow/Decline controls. No reporting occurs before opt-in. Only the versioned preference string is persisted; withdrawal cancels active reports and discards pending dispatches. Storage failures, DNT and Global Privacy Control keep reporting off. Other tabs observe preference changes. Admin pages have no reporter.

The strict request accepts only `{event, consent:true}` and five enums: cart_updated, checkout_reviewed, checkout_confirmed, checkout_failed, client_error. It excludes identity, product/category/cart contents, prices, prescriptions, order details, URLs, messages and stacks. There are no tracking IDs, analytics cookies, third-party SDKs, payload queues or automatic retries. Cart/checkout remain authoritative independently of reporting; replayed confirmations can count twice.

The browser caps two concurrent sends and 20 attempts/minute with two-second cancellation. The uncached Next gateway validates exact origin/CSRF/privacy and strict 128-byte streamed input, bounds input and upstream deadlines, fixes the API destination and strips incoming cookies, authorization and referrers. Express repeats validation and uses existing ingress/rate/deadline guards. It never queries the database for this operation. Request logs omit payloads, identities and query contents. Deployment ingress logging/privacy policy requires separate review.

Operational counts use fixed minute buckets, five/ten-minute snapshots and 10,000/event/minute caps. They are process-local, ephemeral, untrusted and partial; they are not orders, users, affected sessions or a complete error rate. Disabled coverage is explicitly unknown. Existing snapshot readers accept missing additive coverage fields as not configured. An observed client_error raises CLIENT_ERROR_REPORTS for investigation; no report does not establish healthy journeys. Hosting must separately aggregate every instance and configure alert delivery.
