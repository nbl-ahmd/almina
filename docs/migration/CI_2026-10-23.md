# CI and deployment checks — 23 October 2026

Supersedes the required “Modernization foundation” workflow and duplicate
post-merge test run described in earlier migration reports.

## Required CI

`CI` runs once on each PR head, with three parallel jobs:

- Quality: lint, types, unit/release tests and dependency security audit.
- API: HTTP/security tests and disposable MongoDB transaction/integration tests.
- Build: production API/web build and one short production-server HTML/SEO check.

The existing protected `verify` check stays required. Documentation-only changes
(Markdown or files under docs/) skip these application jobs; the classifier and
final gate still run. Workflow, source, dependency, test and unknown-file changes
require the full three jobs. Manual CI runs always run all three.

The entire 130-case Playwright suite, repeated viewport coverage, fixture setup
and the older foundation/storefront smoke scripts are available locally or via
**Browser regression (manual)** in Actions. They no longer block every PR.
Run the relevant browser cases locally for UI, auth, checkout or wholesale changes;
use the full suite for broad frontend changes or release acceptance. Existing
regression tests are preserved, not deleted. No scheduled browser run is added.

The slow job previously spent 8–10 minutes installing browser system dependencies
from the runner's Ubuntu mirror, followed by about 7 minutes of browser cases.
The removed foundation/storefront/SEO smoke combination itself took only seconds.
Actual new hosted timings must be measured; a fixed speedup is not promised.

## Test once, deploy the tested files

Master pushes now trigger **Deploy verified storefront to Vercel** directly.
Its read-only gate finds the actual merged PR and successful latest `CI` run for
that exact PR head, then compares the tested head's Git tree with the merged
release tree. Different files, failed/pending/cancelled checks and missing evidence
block deployment. Older automatic candidates are skipped. Keep strict up-to-date
branch protection and the `verify` requirement enabled. No protection is removed.

An explicit manual CI run on master supports release recovery when no matching
PR exists; only a successful run on the exact candidate qualifies. Manual staging
uses the same gate. Older PRs verified only by the retired foundation workflow do not qualify;
release their desired code through a new reviewed PR with current CI.

Production configuration is pulled privately and the frontend is built for that
configuration as before. This environment-specific deployment build is necessary;
it is not another test-suite run. Contributor/owner requirements of the existing
Vercel project still apply. Render's existing independent master auto-deploy
contract is unchanged; this gate controls Vercel, not Render.

After successful publication, a small read-only check requests the real public
homepage, account, wholesale, robots, sitemap, customer options and API readiness.
A failing post-deploy check reports a failed release; it does not roll back or
place orders. It is availability/response evidence, not a real checkout or inbox
acceptance test.

## Why localhost is correct in CI

A runner starts fresh production-compiled application servers on its own loopback
ports with synthetic fixtures. Integration tests start a disposable MongoDB replica
set and exercise actual transactions and authorization. The test launchers override
origins per server; the old top-level `WEB_ORIGIN` was not a production target.
Production orders, stock and customer records are never test fixtures. Required
CI now scopes synthetic build configuration to the build job instead of displaying
it above every unrelated test job.

## Local commands

- Routine: `npm run lint`, `npm run typecheck`, `npm run test:unit`,
  `npm run test:api`, `npm run test:integration`.
- Production compilation/HTML: `AL_MINA_ISOLATED_BUILD=1 APP_ENV=development
  DATABASE_MODE=disabled WEB_ORIGIN=http://127.0.0.1:3000 npm run build:foundation`,
  then `AL_MINA_ISOLATED_BUILD=1 npm run smoke:seo`.
- Browser: build commerce and foundation first, then
  `npm run test:e2e:smoke -- tests/e2e/next-checkout.spec.ts` (or another affected
  spec). Omit the spec for the full suite; install Chromium once locally if needed.

## Verification of the retained reduction — 8 November 2026

PR #92 still uses this streamlined workflow. `ci.yml` and `browser.yml` have not
changed since the 23 October reduction: three application jobs, a change
classifier and the final required `verify` gate. Browser regression remains
manual. The old test files were retained by that reduction; additional feature
regressions increase individual test-case counts without restoring the automatic
browser suite or duplicate post-merge test runs.

The first PR #92 run passed quality, build and HTTP/API tests, but its database
suite exposed an intermittent concurrent image-import replay race. A caller
could read no completion receipt, then observe another caller's completed
product/item changes and report CATALOG_REVIEW_REQUIRED. The final verify check
correctly failed because the API job failed; these were not two separate faults.

The image importer now rechecks the exact validated manifest's atomic completion
receipt after expected conflicts. It reports a successful replay only if that
receipt exists; stale approvals, changed products, invalid original bytes,
unauthorized calls and incomplete imports retain their existing rejection rules.
Deterministic database-boundary tests cover a competitor overtaking preflight and
the transaction receipt read, with one history entry and unchanged price/stock.
No CI checks were removed, weakened or made optional to hide the failure.
