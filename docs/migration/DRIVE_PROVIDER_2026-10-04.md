# Retained Drive provider ownership

Moves the four duplicated Google Drive clients into a maintained TypeScript raster transport with a lazy compatibility factory. Product/category/banner/poster upload folders, file identifiers, filenames, database contracts and public image URLs remain unchanged. Converted uploads bind requestBody name/parents, MIME and stream bytes; the prior resource alias was supported by the client, so this is consolidation rather than a claim that previous uploads ignored metadata. No delete operation exists.

Each operation has a 15-second deadline, five-MiB input/output limit and at most four concurrent operations per process. Provider retries are disabled. A transport ignoring cancellation keeps its slot until it settles, preventing timeout-driven accumulation. Reads buffer validated WebP/JPEG/PNG bytes before sending response headers; interrupted, malformed, excessive or failed streams are destroyed and provider errors are redacted. Actual decoded uploads still pass the retained Sharp/pixel/format validation before conversion. The raster header check is a delivery restriction, not a substitute for upload decoding.

Construction requires explicit GOOGLE_APPLICATION_CREDENTIALS and preserves the existing drive.file scope. Credential discovery/provider work never occurs during imports/builds. Google Auth uses bounded five-second native-fetch requests without retries; the media client retains its supported Node stream transport. No real credential file was inspected. The existing Google API client remains current; its transitive Node stream dependencies must not be replaced with incompatible browser streams by blind dependency overrides.

Tests cover input rejection, malformed/oversized/stalled streams, deadline cancellation, ignored cancellation, single-attempt uncertain writes, redacted failures, and real googleapis multipart/get behavior against a loopback server. Mandatory disposable MongoDB HTTP coverage exercises all four writers with decoded synthetic rasters, unchanged folder IDs, stable barcode/money/stock, category history lookup, archived product/banner/poster delivery and unchanged metadata/history after an uncertain provider acceptance. The loopback client uses synthetic in-memory credentials and never discovers or contacts Google.

Unknown provider acceptance can still leave an unreferenced upload. Do not automatically retry or delete it; reconcile manually against current/history references. This compatibility adapter does not make legacy creation requests idempotent or replace the signed Cloudinary reconciliation workflow. Before promotion, inventory representative surviving formats/sizes and verify credential scope, every retained image path, provider outage/cancellation, signed replacement and historical references on the accepted host. Five-MiB raster delivery and four concurrent slots are explicit acceptance assumptions; adjust only with measured limits and regression coverage. Store recovery stays closed. No surviving media, database field or production artifact was removed.

Validation evidence is recorded in MIGRATION_STATUS.md. Hosting, real provider acceptance, backup/restore, rotated credentials, traffic observation and order/inventory reconciliation remain release gates. Keep this PR held from master auto-deployment.
